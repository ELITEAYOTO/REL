## Résumé et portée de la méthode

L'architecture actuelle est cohérente pour un laboratoire **statique, CLI-first et offline** : contrats séparés, lecture PE native Rust, CLI d'inspection, producteur d'observations expérimentales indépendant, et comparateur EX-02 **uniquement dans une PR non fusionnée**. Les frontières sont volontairement étroites ; il n'y a pas de raison démontrée de remplacer Goblin, changer de langage ni lancer un refactor global.

Inventaire GitHub : arbre `main` non tronqué contenant **105 fichiers (blobs)** ; lecture ciblée des crates, chemins d'acquisition/publication, prévalidation PE, trois producteurs EX-01, vérificateurs Python, contrats JSON Schema, tests principaux, CI, spécifications, roadmap et politiques d'ingénierie. Les 105 fichiers n'ont **pas** fait l'objet d'une revue exhaustive ligne par ligne : le terme « audit 360° » décrit les axes parcourus, pas une preuve de couverture totale.

Vérifications GitHub constatées : `main` [CI #39191984754](https://github.com/ELITEAYOTO/REL/actions/runs/39191984754) verte ; PR #62, commit `cb123d0`, [CI #39203545918](https://github.com/ELITEAYOTO/REL/actions/runs/39203545918) et [CI #39203551259](https://github.com/ELITEAYOTO/REL/actions/runs/39203551259) vertes sur Windows et Ubuntu. Les CI vertes ne démontrent ni absence de bugs non couverts, ni sécurité hostile, ni fin de la gate EX-02. Aucune campagne longue de fuzz, mesure mémoire représentative, revue externe, ni tests Rust locaux complets n'ont été exécutés **dans cet audit**.

**Classification :** `CONFIRMÉ CODE` = chemin observable dans le dépôt ; `REPRO OS` = reproduction du comportement système, non du CLI REL ; `ÉCART CONTRACTUEL` = désaccord prouvé entre deux règles ; `RISQUE` = menace ou couverture insuffisante, sans incident démontré ; `DETTE` = problème de documentation/processus. Priorités proposées P1 (corriger avant promotion), P2 (avant gate complète), P3 (amélioration).

## Findings prioritaires

### A-01 — P1 — Ouverture de FIFO bloquante dans `rel-diff`

**Statut : CONFIRMÉ CODE + REPRO OS ; test du vrai CLI à ajouter.**  
**Suivi : [issue #63](https://github.com/ELITEAYOTO/REL/issues/63).**

Dans [`tools/rel-diff/src/main.rs`, lignes 75–83](https://github.com/ELITEAYOTO/REL/blob/cb123d0a636406cda48fa9f77f1e6da765c640d9/tools/rel-diff/src/main.rs#L75-L83), `File::open(path)` précède `file.metadata()?.is_file()`. Sous Unix, ouvrir un FIFO nommé en lecture seule **sans `O_NONBLOCK`** peut attendre indéfiniment un écrivain : le contrôle « regular file » arrive trop tard. Une reproduction isolée au niveau OS a confirmé l'attente jusqu'à apparition d'un écrivain. Ce résultat **n'est pas** encore une reproduction par le binaire `rel-diff`.

**Action ciblée :** test subprocess Unix avec `mkfifo`, timeout et nettoyage garanti ; ouvrir les fichiers spéciaux de façon non bloquante avant contrôle du descripteur. Vérifier la politique symlink sans promettre de sandbox. Tester les chemins normaux et le rejet sans émission de JSON sur Windows/Linux.

### A-02 — P2 — Preuve négative absente acceptée par le validateur générique EX-01

**Statut : CONFIRMÉ CODE, test négatif spécifique à ajouter.**  
**Suivi : [issue #64](https://github.com/ELITEAYOTO/REL/issues/64).**

Dans [`scripts/validate_observation_envelope.py`, lignes 43–61](https://github.com/ELITEAYOTO/REL/blob/48fb8e5efa67106c30f03200503c3c164a2be680/scripts/validate_observation_envelope.py#L43-L61), un statut `present` exige une référence de preuve, mais le statut `absent_in_scope` n'exige pas d'`evidence_ids` non vide. Le [schéma EX-01](https://github.com/ELITEAYOTO/REL/blob/main/contracts/experimental/observation-envelope.schema.json) accepte les listes de preuves vides. Mutation proposée : retirer les références de preuve de `fixtures/experimental/observation/absent_in_scope.json` tout en conservant un scope `complete`.

**Portée :** l'acceptation structurelle par ce validateur général n'est **pas** une preuve que le vérificateur distinct `verify_observation_evidence.py` soit contournable ; celui-ci reconstruit les observations des trois producteurs connus à partir des octets. Clarifier l'invariant « absence prouvée » avant de le durcir ; ajouter un test négatif et conserver le contrôle externe.

### A-03 — P2 — Ensemble des entiers JSON Schema plus large que le type Rust

**Statut : ÉCART CONTRACTUEL / limite de représentabilité, pas donnée PE réaliste démontrée.**

Le [schéma public v1](https://github.com/ELITEAYOTO/REL/blob/main/contracts/schemas/binary-manifest.schema.json) définit `size_bytes`, `offset`, `size`, `virtual_address` comme entiers non négatifs **sans maximum** ; la [PR #62](https://github.com/ELITEAYOTO/REL/blob/cb123d0a636406cda48fa9f77f1e6da765c640d9/tools/rel-diff/src/main.rs#L12-L36) les désérialise en `u64`. La règle JSON Schema `integer, minimum:0` accepte notamment `18446744073709551616` et, selon la sémantique numérique, `1.0` ; le désérialiseur `u64` ne représente pas ces cas. Le validateur Python Draft 2020-12 a été interrogé sur ces cas limites, **sans** reproduire séparément le rejet par la CLI compilée.

**Action :** documenter que la lecture EX-02 accepte un sous-ensemble numérique représentable des manifestes strictement conformes, ajouter un oracle aux bornes `u64::MAX` et valeur supérieure, et décider d'une politique d'erreur honnête. **Ne pas changer silencieusement le schéma public v1.**

### A-04 — P2 — Budget de sortie et de mémoire non symétrique entre CLI

**Statut : RISQUE, non mesure RSS.**

[`rel-diff`](https://github.com/ELITEAYOTO/REL/blob/cb123d0a636406cda48fa9f77f1e6da765c640d9/tools/rel-diff/src/main.rs#L205-L235) construit ensembles/collections intermédiaires puis sérialise en une chaîne `serde_json::to_string_pretty` et l'imprime sans plafond de taille de sortie indépendant. Chaque entrée est plafonnée à 16 Mio, donc la taille totale est **indirectement bornée** ; il serait inexact de parler d'une allocation mathématiquement illimitée. Cependant la mémoire transitoire, le coût d'allocations et le volume de sortie ne sont pas contrôlés comme dans [`rel-inspect/src/report.rs`](https://github.com/ELITEAYOTO/REL/blob/main/tools/rel-inspect/src/report.rs).

**Action :** mesurer avec de grandes listes autorisées, définir un budget de rapport et ajouter une régression sans stdout partiel si ce plafond est dépassé. Définir séparément les garanties CPU/RSS inexistantes.

### A-05 — P2 — Politique d'acquisition divergente entre EX-01 et `rel-inspect`

**Statut : RISQUE déjà documenté, non preuve d'exploitation.**

[`rel-observe::load_controlled_file`](https://github.com/ELITEAYOTO/REL/blob/main/tools/rel-observe/src/lib.rs) effectue un `symlink_metadata(path)`, puis `File::open(path)` : une substitution après précontrôle n'est pas liée à une identité de fichier garantie. À l'inverse, [`rel-inspect`](https://github.com/ELITEAYOTO/REL/blob/main/tools/rel-inspect/src/input.rs) dispose de contrôles spécifiques de chemin/descripteur Unix et Windows. Ces limites sont **déjà honnêtement documentées** comme « controlled-only » ; elles deviennent prioritaires avant l'ingestion d'entrées hostiles, mais ne justifient pas à elles seules l'extraction immédiate d'un framework partagé. À rapprocher de [l'issue #9](https://github.com/ELITEAYOTO/REL/issues/9).

### A-06 — P2 — Absence de corpus de validation représentatif et de benchmark EX-02

**Statut : CRITÈRE D'ACCEPTATION OUVERT, pas un nouveau bug.**

La PR #62 possède un oracle sur manifestes contrôlés et un pipeline réel `rel-inspect → rel-diff` sur les deux fichiers PE **synthétiques** du dépôt. Ce n'est ni une comparaison entre 10–20 paires compilées légalement avec changements connus, ni une mesure de la précision, du taux d'abstention, du temps ou du RSS sur corpus représentatif. Cf. [spec EX-02](https://github.com/ELITEAYOTO/REL/blob/main/docs/specs/METADATA_DIFF_PILOT.md) et [issue #15](https://github.com/ELITEAYOTO/REL/issues/15).

### A-07 — P3 — Documentation en décalage temporel

**Statut : DETTE.**

Le [README de `main`, lignes 139–143](https://github.com/ELITEAYOTO/REL/blob/48fb8e5efa67106c30f03200503c3c164a2be680/README.md#L139-L143) annonce EX-01 comme un futur projet alors que trois producteurs expérimentaux et leur vérificateur sont déjà intégrés. D'autres documents expliquent correctement ce statut **partiel**. Éviter « tout est fini » et « rien n'existe ». Harmoniser l'introduction, la roadmap, la stratégie et le handoff lors d'une PR documentaire étroite.

### A-08 — P2/P3 — Reproductibilité, gouvernance et revue indépendante

**Statut : RISQUE + DETTE de processus ; largement déjà recensé.**

- `Cargo.lock` et Rust `1.85.1` sont verrouillés ; CI Windows/Linux exécute formatage, Clippy, tests et release. Point **positif et vérifié**.
- Le workflow utilise des actions par tags (`actions/checkout@v4`, etc.), pas de SHA immuable ; certaines dépendances Python sont bornées par intervalle mais non totalement figées. Les politiques du dépôt demandent une meilleure revue de supply-chain. Ne pas déclarer de vulnérabilité sans audit d'advisories.
- [Licence et politique de contributions : issue #16](https://github.com/ELITEAYOTO/REL/issues/16). Le dépôt public **n'accorde pas à lui seul une licence de réutilisation**.
- PR #62 : **53 commits**, **14 fichiers modifiés**, **1048 ajouts / 3 suppressions**, **aucune review enregistrée** au point figé. La CI verte est une preuve de test, **pas** de revue. Si fusion d'un pilote scoped après corrections, préférer un squash cohérent et une revue du diff.

## Refactor et organisation — décision de l'audit

- `tools/rel-diff/src/main.rs` : **412 lignes physiques** dont des tests intégrés. Dépasse le seuil *souple* Rust de 350 mais reste sous 500. Extraire éventuellement les tests dans `tests/` ou les chargements/contrats dans un module **si** le prochain correctif devient réellement difficile à isoler ; pas de découpage automatique pour une métrique.
- `tools/rel-inspect/src/input.rs` : **499 lignes physiques**, dont de nombreux tests ; proche du seuil dur conventionnel de 500. Envisager de déplacer des tests sans casser les validations d'accès OS, uniquement avec motivation et CI complète.
- `rel-pe` prévalidation et `rel-observe` ont des frontières globalement compréhensibles ; ne pas entreprendre de remplacement général, décompilateur maison ou migration de stack sans cas d'usage et ADR.
