# rel-diff — EX-02 experimental first slice

Compare two pre-generated **controlled PE** binary-manifest v1.0.0 JSON reports:

```sh
cargo run --locked -p rel-diff -- left.json right.json
```

For a separate explicitly requested report that retains warnings:

```sh
cargo run --locked -p rel-diff -- --partial left.json right.json
```

The opt-in result uses [`0.2.0-experimental`](../../contracts/experimental/manifest-diff-partial.schema.json). It nests the unchanged `0.1.0-experimental` metadata report under `observed`; `coverage.status` is `partial` whenever either source has any warning, otherwise `unknown` (not complete). Raw warning strings are preserved and sorted; `negative_behavior_conclusions` is always false. No synthetic ordinal import name is treated as proof of symbol identity. Strict two-argument behavior, input rejection, and the 16 MiB output ceiling remain unchanged.

The output is a separately versioned experimental JSON report governed by [manifest-diff.schema.json](../../contracts/experimental/manifest-diff.schema.json) (`0.1.0-experimental`). Size and architecture change flags, additions/removals of exact import/export strings, and metadata differences for uniquely named sections are compared. Section entries report added/removed/changed exact names with deterministic ordering. Output order is deterministic. Inputs must be regular files and are read from an opened file handle with a 16 MiB + 1 byte ceiling each, decoded with known fields, and extraction warnings or duplicate import/export strings fail closed. The opened handle is checked, avoiding a separate pathname metadata/open race. On Unix, the leaf is opened with `O_NONBLOCK | O_NOFOLLOW` before descriptor validation: FIFO inputs do not stall while waiting for a writer and leaf symlinks are rejected. This does **not** enforce descriptor-relative checks on parent path components, a trusted root, or an atomic snapshot. On Windows, the final component is opened with `FILE_FLAG_OPEN_REPARSE_POINT`, and reparse-point attributes on that same handle are rejected; the open also uses `FILE_SHARE_READ` so ordinary competing writers are excluded while the handle is live. Windows ancestor reparse components, atomic path identity, pre-existing mapped writes and concurrent same-inode writes are **not** globally proven safe. On platforms other than Unix and Windows, ordinary opening may still follow symlinks. The bounded read is not a filesystem trust boundary or an overall memory/CPU sandbox. Section status reports `ambiguous` with no partial section deltas when either input repeats a section name. Otherwise comparison uses exact unique section names and flags changes to file offset, raw size or virtual address; a renamed section appears as removed plus added, not inferred as a rename. Unknown coverage is explicitly reported as a limitation; this is **not** a complete EX-02 implementation, exact JSON Schema validation, function diff, decompilation, security verdict or behavioral proof. Original manifest v1.0.0 stays unchanged.

The experimental `import_dll_case_only` boolean is true only if the exact import sets differ, but lowercasing **only the ASCII DLL prefix before `!`** makes the sets identical without any collisions within either report. Symbol names remain case-sensitive. `imports.added` and `imports.removed` always retain the **original strings**: the hint does not erase or reconcile evidence. False means either there was no raw change or this narrowly defined normalization could not establish case-only equivalence; it must not be interpreted as proof of a behavioral change. The hint covers the **entire** import set, not individual entries. It does not normalize paths, Unicode casing, DLL aliases, ordinal imports or malformed import strings.

Next gate: schema-complete validation, documented duplicate semantics, expanded normalization tests, representative golden fixtures, Windows/Linux CI, and benchmarks on authorized A/B builds. Do not promote EX-02 until those gates pass.

## Resource and numeric compatibility boundaries

The input manifest contract is still **public `binary-manifest v1.0.0`, unchanged**. The experimental Rust reader deliberately supports only nonnegative **JSON integer literals** representable by `u64` (`0` through `18446744073709551615`) for `size_bytes`, `sections[].offset`, `sections[].size` and `sections[].virtual_address`; `null` is accepted for this last, nullable RVA field. The public JSON Schema permits larger nonnegative integers and mathematically integral `1.0` notation; those schema-valid representations are rejected by the CLI, with no partial report. This is a **known partial consumer compatibility limitation** tracked as [#67](https://github.com/ELITEAYOTO/REL/issues/67), not a claim of full JSON Schema acceptance.

Even when each input is at most 16 MiB, both inputs can contribute unique differences. The independent release-binary oracle checks an accepted report above 15 MiB as well as a separate just-over-limit failure with zero stdout. Report serialization therefore has an **independent 16 MiB cap including the final newline**. The full JSON is serialized in memory before any bytes are sent to stdout; if it exceeds this cap, the CLI exits with an error and **no stdout report**. This does not guarantee that an OS-level stdout write cannot fail partway through, nor does it cap all temporary collections, parsing allocations, CPU or RSS. See audit [#68](https://github.com/ELITEAYOTO/REL/issues/68).

The independent CLI oracle also exercises **two schema-valid ~1.1 MiB synthetic manifests** with 2,048 imports, 1,536 exports and 256 sections per side, mixing long names, tab/newline/backslash/non-ASCII characters, disjoint and shared names, and section metadata changes. It checks exact sorted deltas against independent Python set oracles, A/B inversion, byte-identical output under input permutation, abstention on repeated section names and zero-stdout rejection of duplicate imports/exports. This is a bounded correctness test, **not** a measured peak-RSS/CPU ceiling, representative corpus, fuzz campaign or proof against adversarial inputs. Inputs are JSON data; no inspected PE is executed.

`scripts/profile_manifest_diff.py` collects repeated subprocess wall-time and sampled peak RSS/CPU observations with toolchain/runner context on four **synthetic** manifest scenarios (minimal, 8,000 unique imports per side, 2,048 imports + 2,048 exports + 2,048 sections per side with unique and shared changed names, and the accepted near-16-MiB 8,192-import-per-side report). Its runner verifies delta counts before recording observations. A fourth controlled high-cardinality case (`near-report-budget-8192`) exercises a successful JSON report strictly between 15 Mio and 16 Mio, and records the byte size and SHA-256 of complete stdout; repeated runs must agree byte-for-byte. Windows/Linux CI uploads the machine-readable `rel-diff-resource-profile-<os>` artifacts. No performance regression threshold is imposed yet, and sampled RSS may miss short-lived peaks; these numbers are not general-purpose or cross-machine benchmarks. The [captured synthetic Linux/Windows baseline](../../docs/EX02_RESOURCE_BASELINE.md) records historical measurements and the later verified #129 near-limit case, including exact report output SHA-256, PR-head/new-main CI artifacts, environment identity and limitations. Representative legally authorized build pairs remain a separate EX-02 acceptance gate.

## Source-defined compiler-built A/B corpus

Windows CI also generates **8 PE executables from four versions of one controlled C source** using MSVC and LLVM Clang-cl. The independent `pefile` oracle checks `rel-inspect` manifest fields and compares **16 distinct A/B pairs** with `rel-diff`, forward/backward and A/A, with JSON Schema and recorded provenance. These PE outputs are **never executed**. See [EX02 compiler corpus design and captured CI evidence](../../docs/EX02_COMPILER_CORPUS.md). Linux keeps running the synthetic-fixture independent oracle and all Rust tests; MSVC/Clang-cl PE generation is Windows-only. This improves actual compiler-output coverage but is **not** a representative multi-product commercial/open-source corpus and does **not** satisfy the full EX-02 gate.

The corpus builder also supports an **opt-in experimental deterministic-link mode** (`call scripts\\build_windows_diff_pairs.cmd repro`) which keeps the normal builds separate. The diagnostics in [EX02_COMPILER_CORPUS.md](../../docs/EX02_COMPILER_CORPUS.md) confirmed that normal repeat builds differed by only two PE timestamp-field bytes per file, while `/Brepro` produced 8/8 byte-identical builds within a job and matching PE SHA-256s across two distinct CI jobs under the declared toolchain versions. The CI now includes an independent cross-run JSON/ZIP comparator (`scripts/compare_ex02_corpus_runs.py`) and enforces byte identity **only for repeated `/Brepro` builds with matching provenance**, not for ordinary builds. No raw binaries are executed or modified by these diagnostics; different file SHA-256s are never interpreted as a behavioral difference. These observations do not establish a long-term reproducible-build guarantee across SDKs or toolchains.

The core CLI tests now live separately in `src/tests.rs`, keeping the `main.rs` entrypoint focused on manifest handling and report generation.

## Reproducible acceptance checks

Run `cargo test --locked -p rel-diff --all-targets` for the Rust unit and CLI tests. After building `rel-diff` in release mode and installing Python `jsonschema>=4,<5`, run `python scripts/test_manifest_diff_cli.py --binary target/release/rel-diff --inspector target/release/rel-inspect` (append `.exe` to both binaries on Windows). This independent oracle exercises the **actual release CLI** with synthetic, contract-valid v1 inputs and also feeds it manifests produced by the real `rel-inspect` release binary from the tracked synthetic PE32/PE64 fixtures, validates every successful output against the separate experimental JSON Schema, and checks A/A, A/B, B/A, permutation invariance, repeated-byte determinism, casing collisions, ambiguous sections, invalid inputs and the 16 MiB size gate. The Windows/Linux CI runs it after the release build. Its real-inspector path validates a controlled synthetic PE pipeline, **not** extraction accuracy over a representative licensed real-world PE corpus, runtime behavior, memory bounds or a production performance benchmark.
